# v0.0.2 milestone 1: automatic Python dependency discovery

Status: Python inventory implementation is complete within documented format limits, including manifest/workspace reconciliation. Native release validation for the complete v0.0.2 is recorded in its draft/CI evidence. The earlier implementation-increment evidence below is retained as historical proof. See dependency-scanning.md and v0.0.2-security.md for scope and limits.

## Outcome

From a Python project directory, `sentinel scan` discovers supported dependency files, extracts exact package identities, and queries OSV without requiring an SBOM. `sentinel scan --type dependencies` selects the same discovery. SBOM input remains optional and retains its existing inventory-only meaning.

This milestone extends the tested v0.0.1 scanner. It does not complete all agent-protection and intelligence work described in `v002AGENTS.md`, and does not promise universal language coverage. Large-file secrets scanning is a separate follow-up.

## Boundaries and invariants

- Read project dependency files; never install packages, resolve ranges, execute Python, activate environments, or invoke package managers.
- Use public PyPI identities only when the source is established. Do not query private, Git, URL, or local dependencies as if they came from PyPI.
- Keep known packages and findings when another input fails. Malformed, unresolved, unsupported, ambiguous, or bounded-out input makes coverage incomplete (exit 7).
- Preserve CLI flags, policy schema, JSON contracts, audit redaction, OSV/cache behavior, and exit codes. Missing offline intelligence remains incomplete.
- Never include raw dependency lines, credentials, registry URLs, or parser snippets in diagnostics or audit events. Online queries disclose normalized public package names and versions to OSV.
- Preserve discovery exclusions, ignore handling, no-symlink behavior, file/inventory bounds, and deterministic ordering. This scanner does not enforce agent actions.

## Supported inputs and scope

| Input | Planned behavior |
| --- | --- |
| `uv.lock` | Parse explicitly supported schema versions; include exact public-PyPI registry packages across listed groups/platforms. Classify workspace/editable/path/Git/private sources separately. |
| `poetry.lock` | Parse explicitly supported schema versions; include exact public-PyPI packages across listed groups/platforms; honor source metadata. |
| `requirements.txt`, `requirements-*.txt`, `requirements/*.txt` | Parse exact `name==version` pins, extras, hashes, continuations, comments, and recognized environment markers. Follow bounded project-local `-r` includes and apply `-c` constraints. |
| `pyproject.toml` | Identify project roots and declared dependencies/groups/source settings. Reconcile with a usable lockfile; exact public-PyPI pins can be checked without one, with incomplete transitive-coverage diagnostics. |
| Ranges, wildcard pins, unsupported syntax/formats | Explain the missing coverage; do not guess a version. |

Before implementing each parser, verify its current official format specification and representative producer fixtures. Record the exact supported schema versions in documentation and tests; reject newer incompatible versions explicitly. Reuse existing TOML parsing where appropriate. Any new requirement/PEP parser dependency needs a maintenance, licensing, and capability review.

## Discovery and reconciliation

1. Discover candidates recursively using existing traversal safeguards. Recognize nested Python projects and workspace ownership before associating manifests and lockfiles.
2. Group inputs by project/workspace. A recognized manifest covered by a valid corresponding lockfile must not produce the current generic unsupported-manifest warning.
3. Prefer a single authoritative lockfile for that project. If both uv and Poetry lockfiles exist and authority cannot be established, inventory known identities but report ambiguity. Never silently choose a potentially stale lockfile.
4. Process standalone requirements files as separate inventories; do not silently discard them because another lockfile exists. Deduplicate shared exact identities and retain all relevant source locations.
5. Reconcile declared dependencies against lock contents where the format permits. Use producer freshness metadata only when its semantics are implemented and verified. Without that evidence, document that completeness is relative to the supplied inventory, not proof of freshness or environment equivalence.
6. Normalize PyPI names consistently (case and runs of hyphens, underscores, and dots); use PEP 440-aware exact-version handling, not Rust SemVer. Reject ambiguous equality, wildcard and range expressions as unresolved.
7. Include locked optional/development/platform packages conservatively. Validate supported marker syntax without evaluating repository code; document that this inventories listed alternatives rather than simulating the user's installed environment.

Requirements-specific rules:

- Includes must stay inside the selected project root; reject traversal, absolute paths, symlinks, remote includes, cycles, and excessive depth/bytes/file count. Charge includes to shared scan budgets.
- Constraints narrow an existing requirement; they do not introduce dependencies. Resolve only when the intersection establishes one exact version. Conflicts remain incomplete.
- Recognize index directives and direct references before producing public identities. Private/alternate indexes or unresolved source provenance remain uncovered. Never expand environment variables or print embedded credentials.
- A pinned requirements file is not automatically a complete transitive graph. Without authoritative resolution evidence, report limited inventory coverage rather than claiming whole-project completion.
- Do not inspect ambient virtual environments automatically: they may be unrelated to the selected project.

## Architecture and result behavior

- `sentinel-scanner`: add focused Python discovery/parsing modules and an internal typed input-kind dispatch in place of Cargo/npm-only branching. Reuse the normalized inventory, `PyPI` package identities, OSV client, cache, deduplication, and finding model.
- `sentinel-core`: update doctor coverage/capability reporting and project orchestration only as needed.
- `sentinel-cli`: retain current commands; improve actionable human-readable diagnostics without exposing raw input. For example: `requirements.txt: Version range cannot identify an exact package version; provide a supported lockfile.`
- Keep the version-1 JSON envelope/report shape. Add only compatible diagnostic values, checking schema restrictions and downstream contract tests first. Audit records retain allowlisted events and numeric summaries.
- Known findings remain visible in incomplete reports. Complete scans retain exit 0/4 threshold semantics; incomplete coverage takes precedence with exit 7.

## Required tests

- uv and Poetry: valid supported schemas; unsupported versions; malformed TOML; missing names/versions; public/private/path/Git sources; groups, extras, multiple platform versions, workspaces and nested projects.
- Requirements: exact pins, normalization, hashes, continuations, comments, extras, markers, compatible/conflicting constraints, duplicate locations, unsupported options and unresolved ranges.

- Reconciliation: manifest plus lock without false unsupported warnings; manifest-only limitations; multiple conflicting locks; requirements alongside locks; partial failure preserves good packages/findings.
- Mock OSV: correct `PyPI` identities, deduplication, vulnerable and clean responses, fresh offline cache, missing/stale cache, failures, and exact exit 0/4/7 behavior.
- CLI: existing flags/help, parseable single-document JSON, schema validation, stderr separation, human-readable actionable diagnostics and doctor capability changes.

Its large JSONL files remain outside the separate secrets scanner's current size limit.
