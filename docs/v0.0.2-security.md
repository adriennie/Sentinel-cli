# Sentinel v0.0.2 security and operating guide

## Boundary

Sentinel validates local policy and implements a deterministic Claude Code pre-action gate. It is not an operating-system sandbox. Its principal is the local operator; a malicious process with that operator's filesystem access, an administrator, a modified provider binary, or a user who disables/bypasses the guarded client is outside the protection boundary. There is no claim of universal L3 containment. No LLM response grants permission.

`sentinel agent setup claude` merges an exec-form PreToolUse hook into `.claude/settings.json`, backs up an existing file before changing it, records its hash and the Sentinel executable hash, and enables audit integrity. Setup does not launch an agent. It preserves unrelated settings. Invalid settings, symlinks and unsafe storage fail explicitly; an existing incompatible Sentinel hook needs explicit reconciliation.

```sh
sentinel init
sentinel agent setup claude
sentinel agent status
sentinel guard --scope 'src/**' -- claude
```

Guard requires Claude Code 2.1.304 or later within major version 2. The pinned real-client acceptance fixture uses 2.1.304. Before launch, guard checks installation/settings/binary hashes, policy, enabled auditing, audit integrity and provider version. It creates an eight-hour, project-bound nonce and permits one active guarded session per project. Provider version inspection has a five-second timeout. End a previous session before starting another. If a guard process crashed, confirm the provider has stopped before archiving/removing `.sentinel/agent/session.json`; old callbacks then fail closed.

Guard launches the provider in restricted mode with only Sentinel's pre-action settings, disables skills/commands, and supplies an empty strict MCP configuration. Existing user/project hooks, plugins, MCP configuration and environment settings remain on disk but are not loaded as guard configuration. Known hook-disabling environment switches are removed. Managed administrator settings and already-running processes remain outside this guarantee. The [provider's hook protocol](https://code.claude.com/docs/en/hooks) defines `onFailure: "block"`, exec-form arguments and permission decisions. The guard uses these mechanisms instead of interpreting Sentinel's general exit codes as provider permissions.

Only `--print`/`-p`, `--verbose`, `--output-format text|json|stream-json`, and `--max-turns 1..10` are accepted after the provider executable. Settings, safe/bare modes, additional directories, permission overrides, plugins, resume commands and other provider overrides are rejected. Interactive `guard` requires Sentinel's `--format text`; the provider's own output must not contaminate a machine-readable Sentinel envelope. Prompts can be supplied on stdin for print mode.

## Supported action enforcement

- Read, Write, Edit and NotebookEdit normalize their explicit file target. Writes to the selected policy, Sentinel executable, `.git`, `.claude` or `.sentinel` are denied. Access to internal security state and `.env` reads is denied.
- Paths must stay in the selected project. Parent traversal, symlinks, hard links, ambiguous device/alternate-stream syntax and misleading control/bidi characters are rejected. Windows paths resolve existing ancestors to expand short names/canonical casing; guarded file targets are local disk paths, not UNC/device roots. Unicode NFC/case aliases can strengthen policy restrictions; they cannot turn a denial into an allow.
- Bash/PowerShell and unknown tools are denied. Restricted mode additionally removes code-running tools and WebFetch. Arbitrary shell side effects cannot be safely inferred from text, so L0/L1 shell allowances do not enable shell tools in this adapter. Network tools that remain available use the deterministic network policy; L2/L3 deny network actions.
- L0 logs protected writes, L1/L2 require exact-action approval, L2 requires an explicit task scope for writes, and L3 denies supported writes. Explicit deny always precedes approval and allow. A risk score never grants permission.
- Policy, input, session, installation or audit verification failure produces the provider's deny JSON. The installed hook has a ten-second timeout and `onFailure: "block"` so crashes/startup failure/timeouts do not silently authorize the operation.

Metadata checks and the provider's eventual file operation are separate: concurrent same-user replacements are not atomically contained. Hooks do not supervise processes already running, operator shell sessions, provider-internal implementation side effects or arbitrary external clients. Use an independently managed OS sandbox where those threats matter.

## External approvals

```sh
sentinel approvals list
sentinel approvals grant REQUEST_ID --binding EXACT_BINDING_FROM_LIST
```

Pending/granted, unexpired requests display project-relative paths (recognized credential-like names redacted), operation, matched rule IDs, deterministic risk evidence/score and a redacted change preview. Raw tool arguments, commands, proposed contents, old file contents and secrets are not persisted. Review the original proposed change in the trusted client before granting; Sentinel deliberately does not retain a plaintext diff. A protected-path level floor can require approval without a named rule matching.

Local grants are capabilities in owner-private state, not remotely authenticated signed tokens. A grant is bound to normalized operation and exact tool arguments, current target-content hashes, project, provider actor/session, guard nonce, policy/config and risk evidence. It expires five minutes after the original request and is atomically consumed once under a cooperative lock. An identical retry within the same session can consume it even with a new provider tool-call ID; changed arguments, file state, policy, session or risk evidence require a new grant. Noninteractive approval-required calls are denied until an explicit local grant exists. Grant intents and consumption decisions are audited; unavailable audit storage prevents authorization.

State is bounded to 1000 requests and 4 MiB. No approval state is silently pruned. Archive expired/consumed state only with the guarded provider stopped; retain the audit evidence. Deleting pending state revokes its grants rather than authorizing retries.

## Audit integrity and migration

Version-1 `audit.jsonl` event fields and existing `audit` history output remain unchanged. Integrity is opt-in for old projects, and required by agent setup:

```sh
sentinel audit checkpoint --output /path/outside/project/checkpoint-001.json
sentinel audit verify --checkpoint /path/outside/project/checkpoint-001.json
sentinel audit verify --format json
```

The checkpoint command validates existing events, enables `.sentinel/audit-chain-v2.jsonl`, and writes a non-overwriting snapshot outside the project. Canonical payloads sort object keys recursively, preserve array order, and use compact UTF-8 JSON. Chain hashes use SHA-256 over the `sentinel-audit-v2` domain, decimal sequence, previous hash and canonical v1 event. An optional `attachment-sha256` domain plus attachment digest binds detailed agent records into that chain. Initial previous hash is 64 zeroes. Detailed decisions have their own ordered SHA-256 chain over canonical records excluding their current hash; record heads are attached to command summaries. Actor, opaque hashes, rule hashes, reason codes, timestamps and typed risk evidence are stored; no source snippets or raw prompts are stored.

Verification compares event order, sequence/linkage, canonical hashes, decision-journal attachments and optional checkpoint prefix. Modified records, missing evidence and interrupted/inconsistent writes fail verification (exit 8) and block guarded actions. There is no automatic repair or silent truncation. Existing malformed v1 logs must be retained and handled explicitly before establishing a new baseline.

A chain alone cannot detect an attacker rewriting every log and head. An independently retained checkpoint detects truncation below its saved prefix, but the checkpoint is not automatically signed/authenticated. Keep it in separately protected storage and retain old snapshots. Same-user access can rewrite both files unless external controls prevent it. Manual archives start a new evidence epoch; do not imply continuity with the archived chain. Bounds: 32 MiB command log and sidecar, 8 MiB decision journal, 16 KiB per integrity/decision record. Full or unsafe storage fails explicitly.

## Optional analysis and SARIF

```sh
sentinel scan --reachability --entrypoint main.py --python-import requests=requests
sentinel scan --exploit-aware
sentinel scan --offline --exploit-aware --format json
sentinel scan --format sarif > sentinel.sarif
```

Reachability is a conservative Python import prototype, not a call graph or proof that vulnerable code executes. Select up to 32 entrypoints and explicit distribution-to-module mappings. It follows supported static imports through at most 256 project-local modules (1 MiB each), with traversal/symlink rejection. Ambiguous multiline strings, dynamic/relative imports, unsupported ecosystems, missing mappings or missing paths remain `unknown`. It reports potential import reachability when found and never emits `not_reachable` merely because no import was found. Version-1 finding objects stay `not_analyzed`; version-2 analysis records hold the optional evidence.

Exploit enrichment resolves CVE aliases through OSV and looks up [FIRST EPSS](https://api.first.org/epss/) and the [CISA KEV feed](https://www.cisa.gov/known-exploited-vulnerabilities-catalog). Requests disclose advisory/CVE identifiers, not source contents. HTTPS redirects are disabled; connections have five-second and requests twenty-second limits. Responses are at most 16 MiB, aliases 256, KEV entries 50,000, and analysis 1000 findings. New query batches stop after a two-minute budget. EPSS checks at most 32 CVEs per advisory. Unknown/unmapped advisories remain explicit.

Exact-key, versioned cache entries live below `.sentinel/cache/osv-v1/intelligence-v2`. Cache TTL is 24 hours; EPSS source dates must be at most two days old and KEV publication at most seven days old, with no future dates accepted. Invalid/missing/stale data is never a zero probability or negative KEV assertion. Offline mode initializes no HTTP client. A failed refresh can retain stale evidence labelled uncertain. These local caches are not authenticated. Requested analysis gaps make the scan exit 7, preserving findings; they do not turn network failure into a universal agent-development ban.

Shared deterministic scoring caps at 10: protected path +3, destructive operation +4, secret access +4, potential import reachability +2, KEV +3, EPSS >=0.5 +2, uncertainty +1. False evidence flags mean no positive evidence recorded, not proof of safety. A score never weakens explicit policy. Selected entrypoint snapshots bind current source hashes and expire after 24 hours; a guarded edit can consume this advisory risk evidence. Re-scan after dependency or import-graph changes; snapshots are not full graph/freshness attestations.

SARIF 2.1.0 uses stable rule IDs/fingerprints, encoded relative artifact URIs and redacted messages without source snippets. Secret locations retain line numbers; byte columns are omitted because SARIF uses different column units. Incomplete scans mark `executionSuccessful: false`. Optional analysis is in result properties. Tests validate against the vendored OASIS schema; its upstream license is retained separately from Sentinel's MIT license.

## Policy fixtures, PR checks and isolated redteam

```sh
sentinel policy test
sentinel policy test --fixtures fixtures.json
sentinel policy test --changed-files proposed-files.json
sentinel redteam
```

Policy fixtures are JSON arrays of `{ "action": { "action_type": "file.write", "target_paths": ["src/file.rs"] }, "expected": "allow" }`. They only evaluate policy; no proposed write/shell/network action executes. Default tests check built-in level invariants. A measured, bounded policy benchmark accompanies the result. Custom fixture mismatch and denied/unapproved proposed changes exit 5. `--changed-files` is a JSON array of project-relative paths. Require-approval decisions fail closed in this noninteractive CI gate.

The PR workflow reads `sentinel.yml` from the base commit and evaluates proposed writes. It does not accept a more permissive policy from the PR as its baseline. Maintainers must require/protect the status check and security workflow for merge governance; repository owners can otherwise bypass or modify CI. This is not a tamper-proof external merge authority, and there is no automatic GitHub-review-to-approval bridge.

Redteam operates only on disposable synthetic projects and hook JSON. It evaluates self-protection, out-of-scope paths, traversal, shell and unknown-tool attacks without executing attack commands or contacting a model service. Native CI additionally runs the real pinned Claude client against a localhost synthetic Messages API, testing an allowed edit, a protected edit denial and explicit approval consumption. Synthetic credentials and isolated provider configuration are used; no paid model calls are needed.

## Contracts and exit codes

Old commands preserve version-1 data schemas. New commands and enriched scans use `data.schema_version: 2`, a `command` discriminator and typed `result`, inside the unchanged version-1 envelope. See `schemas/v002-output.schema.json` and the unified schema. Provider hook callbacks use Claude's direct decision protocol, and SARIF is emitted directly; neither is wrapped in a Sentinel result envelope. Help/version retain Clap text.

Exit codes: 0 executed/success within scope; 1 storage/unexpected/provider failure; 2 arguments; 3 configuration; 4 threshold findings; 5 policy fixture/proposed-change denial; 6 approval unavailable/changed/expired; 7 incomplete scan or requested analysis; 8 audit verification failure. An `ok` envelope is not a security clearance. Inspect completeness, evidence states, audit status and exit code.
